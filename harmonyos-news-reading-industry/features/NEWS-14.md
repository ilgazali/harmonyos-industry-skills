## When to use

Load this card when the app must **open with content already in it** - a
magazine shelf, an offline dictionary, a catalogue of articles, a starter book
list - and that content is relational enough that a JSON file would be the
wrong shape. The pattern: build the SQLite file offline, ship it in
`resources/rawfile`, copy it once into the RDB sandbox directory on first
launch, and from then on treat it as an ordinary `relationalStore` database
that the app can also write to.

The transferable part is the **copy-once handshake**. A rawfile is read-only
and lives inside the HAP, so `relationalStore` cannot open it in place; it must
be streamed into `<databaseDir>/entry/rdb/<name>.db` first. That copy is
asynchronous and starts in `onCreate`, while the first page's `aboutToAppear`
may run before it finishes - so the two need a rendezvous. This sample uses a
persisted "copy finished" flag plus a bounded retry, which is a simple and
copyable answer.

It generalises to any preloaded dataset: offline maps metadata, a product
catalogue for a shop that works on a plane, seed data for a first-run tutorial.
The same skeleton also covers a database downloaded from the network - swap
`getRawFd` for the downloaded file's descriptor and nothing else changes.

## Feature checklist

- On first launch `book.db` is copied from `rawfile` into the application's
  RDB sandbox directory; on later launches the copy is skipped.
- A flag in `preferences` records that the copy completed, and is flushed so it
  survives a restart.
- The magazine page opens a `relationalStore` store named `book.db` and queries
  the `book_list` table.
- Each row becomes a `Book` (id, title, author, cover, content, desc, userType).
- If the page loads before the copy finishes, the read retries up to three
  times at 500 ms and then resolves empty rather than throwing.
- The list renders three per row through `LazyForEach` over an `IDataSource`.
- A 全部 / VIP tab pair switches between the full list and the
  `userType === 1` subset; VIP items carry a badge in the corner of the cover.

## Architecture

One `entry` module, seven ArkTS files, plus one third-party HAR for the tab
bar.

```
entry/src/main/ets
├── data/DBOperatorManager.ets       copy-to-sandbox + getRdbStore + query; module singleton
├── data/SpManager.ets               tiny preferences wrapper (getBoolean/putBoolean, always flushed)
├── entryability/EntryAbility.ets    publishes context to AppStorage, kicks off the copy, avoid areas
├── entrybackupability/EntryBackupAbility.ets
├── model/BasicDataSource.ets        generic IDataSource with listener plumbing
├── model/Book.ets                   the row class + the two tab items (全部 / VIP)
├── model/BookDataSource.ets         BasicDataSource<Book>
└── pages/PresetBookPage.ets         @Entry - tab options, the LazyForEach grid, the VIP filter
entry/src/main/resources/rawfile
├── book.db                          the preset SQLite database
└── book1..book13.png                covers, referenced by name from the `cover` column
```

The documented tree names `pages/Index.ets`; the zip has `pages/PresetBookPage.ets`
and no `Index.ets` (`HW-11-0015`). The document's own step-2 snippet is headed
`// PresetBookPage.ets`, so the tree contradicts the page beside it. The tree
also omits the `@piaojin/pjtabbar` dependency declared in `entry/oh-package.json5`,
which a reader will discover only when the build fails to resolve `PJTabComponent`.

**The design decision worth copying** is that the *cover images stay in
rawfile* and the database stores only their file names. The `cover` column
holds `book3.png` and the view does `Image($rawfile(book.cover))`. That keeps
the shipped `.db` small and text-only - it diffs, it can be regenerated by a
script, and no BLOB handling is needed on either side. The database carries
identity and metadata; the HAP carries bytes. The same split is what lets a
later version replace covers without touching the database, or replace the
database without re-packing the images.

## Implementation steps

1. **Publish the ability context early.** `EntryAbility.onCreate` does
   `AppStorage.setOrCreate<Context>('context', this.context)` before anything
   else, because `SpManager`'s constructor reads it synchronously.
2. **Start the copy in `onCreate`,** not in the page. It is the earliest point
   at which a context exists, and it gives the copy a head start over the first
   `aboutToAppear`.
3. **Guard the copy with a persisted boolean.** Read it in the manager's
   constructor; return immediately when it is already true. Write it with
   `putSync` **followed by `flushSync`** - `putSync` alone is memory-only and
   the flag would be lost on restart, re-copying the database every launch.
   (The sibling `WebFontSize` sample gets exactly this wrong; see `NEWS-16` and
   `HW-11-0018`.)
4. **Create the RDB directory chain before opening the destination file:**
   `<databaseDir>/entry`, then `<databaseDir>/entry/rdb`.
5. **Stream the rawfile in fixed-size chunks** with `fs.read`/`fs.write`,
   starting at the descriptor's `offset` - a rawfile descriptor points into the
   HAP, so offset 0 is not the start of your file.
6. **Detect the end of the copy by a short read** (`readLength < bufferSize`)
   and set the flag there, inside the loop, before breaking.
7. **Open the store by name only.** `relationalStore.getRdbStore(context,
   { name: 'book.db', securityLevel })` resolves to the file you just wrote
   into the RDB directory; the path is never spelled out.
8. **Rendezvous with a bounded retry.** `readBookList(context, 3)` recurses
   through a 500 ms `setTimeout` while the flag is false and resolves `[]` when
   the budget runs out, so the UI degrades to empty instead of hanging.
9. **Close the `ResultSet`** as soon as the rows are copied out - the sample's
   own comment is right that leaking it leaks an fd.
10. **Feed the list through an `IDataSource`,** and derive the VIP tab by
    filtering the same array into a second data source rather than querying
    twice.

## Verified snippets

All snippets are from `PresetBook.zip`.

**Streaming the rawfile into the sandbox — `entry/src/main/ets/data/DBOperatorManager.ets`** (as shipped)

```typescript
copyDBToSandbox(context: Context, dbName: string) {
  if (this._isDBCopyFinished) {
    hilog.info(DOMAIN, TAG, 'db has copy finished.');
    return;
  }
  context.resourceManager.getRawFd(dbName, (error, value) => {
    if (error || !value) { return; }
    this.saveFileToSandbox(context, value, dbName);
  });
}

private async saveFileToSandbox(context: Context, file: resourceManager.RawFileDescriptor, dbName: string) {
  let cacheFile: fs.File | null = null;
  try {
    let dirPath = context.getApplicationContext().databaseDir + '/entry';
    fs.mkdirSync(dirPath);
    dirPath = dirPath + '/rdb';
    fs.mkdirSync(dirPath);
    const dbFileDir = context.getApplicationContext().databaseDir + '/entry/rdb/' + dbName;
    cacheFile = await fs.open(dbFileDir, fs.OpenMode.READ_WRITE | fs.OpenMode.CREATE);

    const bufferSize = 10224 * 1024;
    let buffer = new ArrayBuffer(bufferSize);
    let readOption: ReadOptions = {
      offset: file.offset,     // the rawfile lives INSIDE the HAP - start at its offset, not 0
      length: bufferSize
    };
    while (true) {
      let readLength = await fs.read(file.fd, buffer, readOption);
      await fs.write(cacheFile.fd, buffer, { length: readLength });
      if (readLength < bufferSize) {          // short read == end of file
        this._isDBCopyFinished = true;
        getSpManager().putBoolean(SP_DB_COPY_FINISHED, true);
        break;
      }
      if (readOption.offset !== undefined) {
        readOption.offset += readLength;
      }
    }
  } catch (error) { /* logged */ } finally {
    fs.close(cacheFile);
  }
}
```

**`file.offset` is the line that makes this work.** `getRawFd` does not hand
back a private file - it hands back the HAP's own descriptor plus the offset
and length of the entry inside it. Reading from 0 would copy the archive
header. Every subsequent iteration advances `readOption.offset` by the bytes
actually read, so the loop walks the entry rather than the archive.

**The termination condition is a short read, not `file.length`.** That is
robust as long as the buffer is genuinely larger than any tail chunk, and it is
why the completion flag is set inside the loop rather than after it. Note the
buffer is `10224 * 1024` - almost certainly a typo for `10240 * 1024` (10 MiB),
harmless because it is only a chunk size, but a reminder that the constant is
arbitrary. It also means a database larger than the buffer is written in
several passes, while one smaller than it - as here - is a single read/write.

The `finally` block calls `fs.close(cacheFile)` unconditionally, including on
the path where `fs.open` itself threw and `cacheFile` is still `null`. Type it
as nullable, as the sample does, and then actually check it before closing.

**The copy/read rendezvous — same file** (as shipped)

```typescript
readBookList(context: Context, retryTimes: number): Promise<Book[]> {
  if (this._isDBCopyFinished) {
    return this.readBookListAfterDBCopied(context);
  }
  // 如果db没有拷贝完成且需要重试，则延迟500ms后重试。
  if (retryTimes <= 0) {
    return Promise.resolve([]);
  }
  return new Promise<Book[]>(resolve => {
    setTimeout(() => {
      resolve(this.readBookList(context, --retryTimes));
    }, 500);
  });
}
```

**This is the whole synchronisation mechanism**, and it is worth being explicit
about what it is: polling with a budget. `copyDBToSandbox` returns before the
copy is done, so the page cannot await it; the flag is the only shared signal.
Resolving the outer promise *with* the recursive call chains the retries into
one promise the caller awaits once, which is the neat part.

Its limits are equally clear. Three retries at 500 ms is 1.5 s; a larger
database or a slow device silently yields an empty shelf with no error state,
and the flag is only set at the end of a successful copy, so a copy that fails
half way leaves a truncated `book.db` in the sandbox that the next launch will
happily try to open. A production version should hold a promise (or an
`AppStorage` signal) that the copy resolves, and delete the partial file in the
`catch`.

**Query into typed rows — same file** (as shipped)

```typescript
readBookListAfterDBCopied(context: Context): Promise<Book[]> {
  const bookArray: Book[] = [];
  return new Promise<Book[]>(resolve => {
    const STORE_CONFIG: relationalStore.StoreConfig = {
      name: 'book.db',
      securityLevel: relationalStore.SecurityLevel.S3
    };
    let predicates = new relationalStore.RdbPredicates('book_list');
    relationalStore.getRdbStore(context, STORE_CONFIG)
      .then(async (rdbStore: relationalStore.RdbStore) => {
        rdbStore.query(predicates, async (err, resultSet) => {
          if (err) { return; }
          // resultSet是一个数据集合的游标，默认指向第-1个记录，有效的数据从0开始。
          while (resultSet.goToNextRow()) {
            const book: Book = {
              id: resultSet.getLong(resultSet.getColumnIndex('id')),
              title: resultSet.getString(resultSet.getColumnIndex('title')),
              author: resultSet.getString(resultSet.getColumnIndex('author')),
              cover: resultSet.getString(resultSet.getColumnIndex('cover')),
              content: resultSet.getString(resultSet.getColumnIndex('content')),
              desc: resultSet.getString(resultSet.getColumnIndex('desc')),
              userType: resultSet.getLong(resultSet.getColumnIndex('user_type'))
            };
            bookArray.push(book);
          }
          // 释放数据集的内存，若不释放可能会引起fd泄露与内存泄露
          resultSet.close();
          resolve(bookArray);
        });
      })
      .catch((err: BusinessError) => {
        resolve(bookArray);      // resolves empty rather than rejecting
      });
  });
}
```

**`StoreConfig.name` is a name, not a path** - `getRdbStore` looks in the
application's RDB directory, which is exactly where `saveFileToSandbox` wrote
the file. Get the copy destination wrong by one directory level and this call
silently creates a *new*, empty `book.db` instead of opening the preset one:
the query then fails on a missing `book_list` table rather than telling you the
copy path was wrong. That failure mode is the main reason to keep the
destination path spelled out in one place.

`securityLevel: S3` classifies the content as sensitive. For a public magazine
catalogue S1 would be the honest level; the level is recorded when the store is
created and **cannot be lowered afterwards**, so it is worth choosing
deliberately the first time.

The cursor idiom is standard: `goToNextRow()` advances and returns false past
the last row, so the whole read is a `while`. `getColumnIndex` is called per
column per row here, which is fine for thirteen rows and worth hoisting for
thirteen thousand. `resultSet.close()` before `resolve` is not optional - the
comment above it is Huawei's own warning about the fd leak.

**Rendering and the VIP filter — `entry/src/main/ets/pages/PresetBookPage.ets`** (as shipped)

```typescript
@Builder
BookItem(book: Book) {
  Stack({ alignContent: Alignment.TopEnd }) {
    Column() {
      Image($rawfile(book.cover))          // the DB stores only the file name
        .aspectRatio(1)
        .borderRadius(8);
      Text(book.title).fontSize(14).padding(2);
    }
    .alignItems(HorizontalAlign.Start)
    .borderRadius(12)
    .clip(true);

    Image($r('app.media.icon_vip'))
      .width(24)
      .visibility(book.userType === 1 ? Visibility.Visible : Visibility.None);
  };
}

@Builder
TabItemPage($$: PJReferenceTabBarItemInterface) {
  List({ space: 16 }) {
    LazyForEach($$.currentItemIndex === 0 ? this.data : this.vipData, (item: Book) => {
      ListItem() { this.BookItem(item); };
    }, (item: string) => item);
  }
  .lanes(3, 8)
  .cachedCount(18);
}

filterVipData(bookArray: Book[]) {
  const vipArray = bookArray.filter(book => book.userType === 1);
  this.vipData.reloadData(vipArray);
}
```

**`lanes(3, 8)` is why this is a `List` and not a `Grid`.** Three columns with
an 8 vp gutter gives the shelf layout while keeping `LazyForEach` recycling and
`cachedCount`, which a `Grid` would also offer but with more configuration.
`cachedCount(18)` is six rows - one screen ahead and one behind.

**The VIP tab is a second data source over the same query result**, not a
second query. One read, two projections; switching tabs never touches the
database. That is the right call for a catalogue of this size and the reason
`filterVipData` takes the array rather than re-reading it.

Two things to fix before reuse. The `LazyForEach` key generator is typed
`(item: string) => item` over a `Book[]` - it returns the object where a string
is declared, so keys are whatever the runtime stringifies, and two rows with
equal field values would collide. Key on `item.id.toString()`. And `BookItem`
is a `@Builder` taking a `Book` by value: inside a `LazyForEach` that rebuilds
the whole subtree on any change; a `@Component` with `@ObjectLink` (or
`@Reusable`) is the scalable form.

## Permissions & config

**None.** The sample declares no `requestPermissions` - a preset database and
its images are all local.

`entry/oh-package.json5` depends on `@piaojin/pjtabbar` `^1.1.6`, a third-party
tab bar HAR that supplies `PJTabComponent` and the ~18 `PJTabBarOptions`
properties configured in `aboutToAppear`. The document neither mentions it nor
lists it in the tree. If you are lifting this sample, the tab bar is the one
part with an external dependency, and ArkUI's own `Tabs`/`TabContent` with a
custom `tabBar` builder covers the same pill-indicator look.

`EntryAbility.onCreate` pins light colour mode and publishes the context to
`AppStorage` under the key `'context'`; `SpManager`'s constructor reads that key
synchronously, so the two are order-coupled - construct `SpManager` before the
ability runs and it gets `undefined`.

## Constraints

- API Version 20 Release or later; HarmonyOS 6.0.0 Release SDK or later;
  DevEco Studio 6.0.0 Release or later. `compatibleSdkVersion` in the zip is
  `6.0.0(20)`, matching the document.
- The preset database is read-only in practice: the sample never writes to it,
  and any write would be lost the moment a new HAP version re-triggers the
  copy. Version the flag key (or the file name) if the app is expected to write
  rows and later ship an updated preset.
- The copy is not idempotent against interruption - see the rendezvous snippet.
- `display.getDefaultDisplaySync().width` is read once in `aboutToAppear` to
  size the two tab items at half the content width. On a foldable or a resized
  2in1 window the tab bar does not re-measure.
- `fs.close(cacheFile)` in the `finally` runs even when `cacheFile` is `null`.
- `SpManager` holds a non-optional `preferences.Preferences` initialised from
  `AppStorage.get<Context>('context')`, which is typed as possibly undefined -
  `getPreferencesSync` will throw if the manager is ever constructed first.

## Pitfalls

- **`HW-11-0015`** (E/low, confirmed): the 工程目录 tree lists
  `pages/Index.ets` (`// 入口界面`), but the zip contains
  `entry/src/main/ets/pages/PresetBookPage.ets` and no `Index.ets`; the
  document's own step-2 snippet is headed `// PresetBookPage.ets`, so the page
  and its tree disagree inside one document. **Fix:** regenerate the tree from
  the zip - replace `Index.ets` with `PresetBookPage.ets` - and add the
  `@piaojin/pjtabbar` dependency, which the tree also omits.
